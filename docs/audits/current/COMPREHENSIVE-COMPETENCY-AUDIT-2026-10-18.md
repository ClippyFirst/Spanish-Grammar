# Комплексний аудит довідника Gramaticarrona — 2026-10-18

**Гілка:** docs/grammar-reference-architecture-2026-10-18  
**Тип:** комплексний source-level аудит із матрицею компетенцій, перевіркою вимог, оцінкою достатності бази й планом закриття прогалин.  
**Рішення:** база тем і технічна архітектура достатні як фундамент; доказова й редакційна перевірка контенту ще недостатня для заяви про повністю перевірений довідник.  
**Обмеження:** звіт не приписує непроведені browser-тести, корпусні пошуки або лінгвістичний фактчек кожній статті. QA-успіх означає проходження конкретних автоматичних перевірок, а не наукову верифікацію всіх тверджень.

## 1. Відповідь на головне питання

**Чи достатня база?** Так — як тематичний і технічний каркас для повноцінного граматичного довідника. Ні — якщо під «достатньою» розуміти, що кожне правило, приклад, український переклад, регіональна позначка й зв'язок між статтями вже перевірені та готові отримати статус verified.

Не рекомендую зараз безсистемно додавати десятки нових статей або новий фреймворк. Правильний наступний крок — не нарощування обсягу, а **перевірка глибини, доказовості та узгодженості наявного контенту**, після якої додавати лише підтверджені прогалини.

| Браузерна доступність і реальний UX | **Не доведені** | Потрібен ручний браузерний прохід за ключовими маршрутами та viewport |
| Навігація / граф тем | **Структурна основа є; семантика потребує вибіркового аудиту** | Формальні лінки й змістові відношення — різні перевірки |

## 2. Матриця компетенцій довідника

Шкала статусів:
- **A — фундамент наявний:** є модель/файл/інструмент, що підтримує компетенцію.
- **B — структурно покрито:** є тематичні сторінки або маршрут, але глибину ще не підтверджено для всього корпусу.
- **C — частково перевірено:** є конкретний аудит/докази для обмеженої вибірки.
- **D — не перевірено / бракує доказів:** не можна заявляти про завершеність.

| Компетенція | Що має вміти довідник | Наявна база / доказ | Статус | Що потрібно |
|---|---|---|---|---|
| K01. Фонологія й орфографія | Пояснювати читання, наголос, тільди, орфографічні зміни й межі графемно-фонемних узагальнень | Є блок spelling/fundamentals і сторінки в контентній карті | B | Перевірити парадигми, винятки та узгодженість прикладів; не змішувати вимову з орфографією |
| K02. Морфологія іменника | Рід, число, узгодження, винятки, лічильність, складні випадки | Є категорія nouns та зіставлення з чеклістом | B | Наскрізна перевірка винятків, множин, узгодження й термінології |
| K03. Артиклі й детермінативи | Визначеність, нульовий артикль, нейтральне lo, частини тіла, власні назви | Є окремий блок articles та пов'язані теми | B | Пріоритетний фактчек через високу контрастивну складність для української |
| K04. Прикметники й прислівники | Узгодження, позиція, зміни значення, квантифікація й фокус | Є дві тематичні категорії | B | Перевірити лексичні пари, контрприклади та перетини з прагматикою |
| K05. Займенники й клітики | Функції, порядок, дублювання, se, узгодження й обмеження конструкцій | Є спеціалізовані статті; одна стаття про позицію клітик пройшла пілотний source review | C | Повний набір контекстів, акцентуація, регіональні обмеження й регресійні приклади |
| K06. Прийменники й керування | Значення, керування, колокації, контрастивні межі | Є категорія prepositions і сторінки por/para та керування | B | Звірити керування за словниками/академічними джерелами; не виводити частотність із загального правила |
| K07. Часи й аспект | Значення, часові перспективи, аспектуальна перспектива, контекстні контрасти | Є огляд часів і спеціальна сторінка indefinido/imperfecto | C | Перевірити приклади, зокрема saber/conocer/querer; окремо відстежити perfecto compuesto vs indefinido за регіонами |
| K08. Способи, модальність і subjuntivo | Сфера дії, тригери, заперечення, прагматика й контрприклади | Є категорія moods і пов'язані сторінки | B | Потрібен source-based audit тригерів і мінімальних контрастів, а не лише перелік сполучників |
| K09. Дієслівні перифрази | Вибір форми, значення, порядок клітик, обмеження | Є окрема категорія periphrases | B | Перевірити, де клітики можуть/не можуть пересуватися, та відмежувати продуктивні моделі від лексикалізованих |
| K10. Синтаксис речення | Порядок слів, питання, заперечення, пасив, підрядність, інформаційна структура | Є велика категорія sentence-structure | B | Перевірити природність контекстів і не описувати прагматичні тенденції як жорсткий синтаксис |
| K11. Словотвір і мікроконструкції | Продуктивність, значення, регістр, полярність і фокус | Є категорії word-formation та micro-constructions | B | Для кожної конструкції вказати сферу застосування, контрприклад і джерельний статус |
| K12. Регіональна компетенція | Розрізняти загальноіспанське, Іспанію, макрорегіони, країни, спільноти та регістри | Створено регіональну матрицю, але статуси не перевірені | D | Аудитувати лише релевантні конструкції, однак на рівні країни/зони там, де це потрібно |
| K13. Контрастивна українсько-іспанська компетенція | Пояснювати функціональні відмінності без механічних кальок | Є правила розробки й карта інтерференцій | C | Окремий прохід за українськими перекладами, кальками й надто широкими аналогіями |
| K14. Джерельна цілісність | Прив'язувати ключове твердження до конкретного академічного/описового джерела | Додано sources до трьох канонічних сторінок; схема дозволяє масив рядків | C | Визначити критерії reviewed і verified; за можливості зберігати назву, розділ, тип джерела й охоплене твердження |
| K15. Природність і походження прикладів | Розрізняти авторські, адаптовані та засвідчені приклади; не вигадувати корпусну частотність | Стандарт це визначає; загальний корпусний аудит не підтверджено | D | Перевірити критичні приклади й походження; корпус використовувати для конкретних питань, а не автоматично для кожної статті |
| K16. Українська мова пояснення | Граматичність, термінологічна послідовність, ясність від початківця до просунутого читача | Є стильові правила й кілька точкових редакцій | C | Повний мовний прохід за абзацами, прикладами й перекладами |
| K17. Дидактична ясність | Від короткої відповіді до нюансів; мінімальні пари, контрприклади, діагностичні питання | Стандарт якості створено; пілот виявив суперечність між двома сторінками ser/estar | C | Застосувати чекліст до пріоритетних статей; не нав'язувати однакову структуру коротким темам |
| K18. Навігація й карта понять | Канонічні теми, передумови, контрасти, винятки й необов'язкові шляхи | Є типізовані зв'язки та graph audit | B | Окремо перевірити семантичну корисність зв'язків, а не лише резолюцію URL |
| K19. SEO та індексація | Коректні маршрути, метадані, sitemap/canonical, корисні заголовки й пошук | Є build, Pagefind і статичні перевірки; повний зовнішній SEO-аудит не підтверджено | B | Перевірити згенерований HTML, sitemap, canonical, robots і реальні search snippets |
| K20. Доступність і responsive | Клавіатура, focus, контраст, семантика таблиць, zoom і мобільне читання | Є дизайн-скрипти; ручного браузерного аудиту не підтверджено | D | Ручна перевірка клавіатури, 200% zoom, вузького viewport, таблиць, skip link і reduced motion |
| K21. Візуальне пояснення | Використовувати графіку лише за доведеної користі, з текстовим еквівалентом | Додано skill аудиту візуалізацій у sibling PR #26 | C | Застосовувати за потребою; текст/таблиця/відсутність графіки — повноцінні результати |
| K22. Технічна підтримуваність | Один source of truth, стабільні URL, передбачуваний QA і простий статичний деплой | Архітектура, схема, registry, helpers і QA pipeline описані | A | Зберігати архітектурний freeze; зміни — тільки на підставі виміряного дефіциту |
| K23. Релізна перевірка | Відтворюваний QA плюс ручний smoke test після build | npm run qa визначено як агрегований gate; ручний браузерний прохід не підтверджено | C | Перед релізом додати короткий документований browser smoke test |
| K24. Редакційна прозорість | Розрізняти draft/reviewed/verified та явно показувати межі впевненості | Статуси є в схемі й документах; у пілоті reviewed ≠ verified | C | Не підвищувати статус автоматично; записати критерії та застосовувати послідовно |

## 3. Матриця регіонального охоплення: рішення

Наявний реєстр регіонів широкий і корисний: загальноіспанська норма/опис, нейтральний редакційний регістр, різновиди Іспанії, Мексика, Центральна Америка, Кариби, північ Південної Америки, Анди, Чилі, Ріоплатенський регіон, Парагвай, США, Екваторіальна Гвінея та інші контактні/діаспорні контексти.

Але **перелік регіонів — не доказ покриття**. Поточний статус матриці: рамка є; усі країно-регіональні клітинки лишаються «не перевірено». Це правильно й чесно. Не потрібно додавати в кожну статтю список усіх країн. Потрібно:
1. виявити регіонально чутливі твердження;
2. записати точне твердження, регістр і сферу;
3. знайти джерело, яке охоплює саме цей регіон/спільноту;
4. позначити результат як підтверджений, обмежений, варіативний, неперевірений або недостатньо доказів;
5. змінювати статтю лише коли висновок впливає на пояснення читачеві.

### Регіональні P0 для першого проходу
- звертання й займенники: tú, vos, usted, vosotros, ustedes, змішані системи;
- форми voseo та імперативи;
- розподіл pretérito perfecto compuesto / indefinido;
- клітики й leísmo/laísmo/loísmo, якщо тема цього потребує;
- subjuntivo та модальність у конкретних конструкціях.

## 4. Матриця навичок (skills) і маршрутизація

За інвентаризацією в окремому PR #26 описано 29 project-specific skills. Для цього довідника кількість сама по собі не є KPI. Важливіше, щоб кожна навичка мала чіткий власний результат і запускалася лише за релевантності.

| Форми, орфографія, парадигми | Коректність форм та узгодженість таблиць | Forms auditor для локальної зміни; paradigm auditor для наскрізних таблиць | Не запускати обидва без окремої потреби |

| SEO, accessibility, браузер і HTML | Зовнішній HTML, клавіатура, viewport, індексація | Перед релізом або після UI/маршрутних змін | Не дублювати npm QA без конкретної додаткової перевірки |

### Висновок про skills
29 навичок достатньо для стартової редакційної системи; наразі немає доказів, що потрібно додавати ще десятки. Перш ніж розширювати набір, треба перевірити, що існуючі навички:
- мають позитивні, негативні й неоднозначні тест-кейси;
- повертають конкретні findings з доказом;
- не дублюють автоматичний QA;
- не виконують непотрібний повний прохід на кожній дрібній зміні;
- не підміняють джерела впевненим тоном.

## 5. Джерельна модель і статуси редакції

### Поточна проблема
Схема контенту має sources: string[], review_status: draft | reviewed | verified та необов'язкові updated і region. Це добрий backward-compatible початок, але сама наявність поля sources не гарантує, що посилання відкрите, веде до правильного місця, підтримує конкретне твердження, має належний тип джерела або достатнє для географічного охоплення.

### Запропоновані критерії статусу
- **draft:** матеріал створено або суттєво змінено, перевірка ще не завершена.
- **reviewed:** редактор пройшов зміст, приклади й джерела в межах явно описаної сфери; відкриті питання залишено в аудиті. Це не означає, що кожне твердження повністю верифіковане.
- **verified:** усі твердження високого ризику прив'язані до придатних джерел; форми та приклади перевірені; переклади й регіональні позначки перевірені там, де релевантно; немає невирішених P0/P1 у межах заявленої сфери; є запис доказів і QA для зміненої сторінки.

**Не підвищувати старі сторінки до verified масово** через успішний build або наявність джерел у frontmatter.

## 6. Технічна архітектура та QA

### Що достатньо
- Astro + MDX + TypeScript і статичний деплой — адекватний вибір.
- MDX-контент є джерелом істини; категорії та URL централізовані.
- Семантичні зв'язки розділені на related, prerequisites, contrasts, extensions, exceptions.
- npm run qa охоплює typecheck, MDX preflight, таблиці, content validation, links, graph, design audits, final content audit та build.
- Документація архітектури й правил розробки достатня для дисциплінованих вузьких змін.

### Що QA не доводить
- правильність кожного граматичного правила;
- природність усіх іспанських прикладів;
- коректність усіх українських перекладів;
- повноту регіонального охоплення;
- фактичну працездатність усіх маршрутів у браузері на різних viewport;
- доступність за реальною клавіатурною навігацією та скринрідером;
- актуальність усіх зовнішніх джерел.

### Релізний smoke test, якого бракує
Перед релізом вручну перевірити: головну, пошук Pagefind, одну сторінку кожної основної категорії, порівняльну сторінку, внутрішні canonical links, мобільний viewport, zoom 200%, клавіатурний фокус, skip link, таблиці та MDX-компоненти. Занести дату, браузер, viewport і результат. Не заявляти про browser audit без такого запису.

The same sample confirmed that some related pages overlap substantially (`pronouns/personal-a` vs `sentence-structure/personal-a`; `verbs/gustar` vs `verbs/gustar-type-verbs`; two article pages). This is a content-information-architecture issue to resolve with explicit page roles and reciprocal links, not by blindly deleting one URL. The current audit therefore increases confidence that the architecture is usable while also confirming that the existing corpus needs editorial reconciliation beyond structural QA.

The first run after the comparison rewrite failed because the new `CompareTable` did not match the component's column schema. The first attempted correction still supplied two data cells where a label column plus one data cell was expected; the table was then corrected to two header entries and one data cell per row. Final QA status must be read from the latest run for the current PR head, not from an earlier successful commit.


### Route integrity finding

The follow-up audit also found that comparison content IDs included the `.mdx` extension in generated route parameters, even though authored links and canonical URLs omitted it. The shared comparison URL helper and static route now normalize source extensions, and the link audit checks comparison URLs as well as grammar URLs. The prior checker had not validated `/comparisons/...` links, so its earlier zero-problem result did not cover this route family. This is a concrete reason to keep route/build checks distinct from linguistic review.
